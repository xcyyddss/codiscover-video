# 阶段边界与优化路线

第一阶段以完整、可运行的协作闭环为交付标准；第二阶段应选择少量已有模块做可测量的工程优化。当前没有把“换一个框架”当成优化结果，也没有声称已证明真实用户满意度提升。

## 第一阶段已实现的范围

- 单用户本地工作台：目标、在线对话、可编辑意图、视频/自由反馈、导入、知识库和任务界面。
- 两种运行模式：无凭证合成演示，以及真实 B 站只读采集与 DeepSeek Flash。
- 采集和证据：字幕与时间戳、有限故事板帧、元信息降级、需要登录时暂停。
- 本地记忆：SQLite WAL、内容切块与 FTS 索引、目标内反馈、导出与清除。
- 离线探索：定时触发、有界执行、重复任务合并、取消恢复、检查点与用量记录。
- 推荐：BM25 + 词法哈希向量融合、明确负偏好过滤、反馈分数与 MMR 多样性选择。
- DSH：原生 8 工具桥接与独立只读 MCP 采集边界。
- 验证：协议、工作流、检索与并发测试，固定合成语料评估脚本。

各项“实现”不自动等于所有真实环境已验证。真实平台、模型账户和 DSH UI 的验收应以对应运行记录为准。第一阶段不包含平台内部推荐流、跨用户行为矩阵、创作者后台、云端多用户部署或全片 ASR。

## 第二阶段先建立评估基线

选定一个真实使用场景，例如“下班后的低负担观看”，构造独立于开发素材的查询、视频证据与相关性标注。保留调参集和测试集，不用同一批演示素材同时设计规则和证明质量。

| 维度 | 建议测量 | 避免的误解 |
| --- | --- | --- |
| 检索 | Recall@K、nDCG@K、无关查询拒答率 | 合成样例命中不代表泛化能力 |
| 内容证据 | 引用准确率、可追溯率、证据状态分类 | “有引用”不等于引用支持结论 |
| 交互 | 澄清后目标一致性、拒绝/改口正确率、用户负担 | 多问几轮不必然更懂用户 |
| 执行 | 任务成功率、恢复成功率、请求/视频耗时、调用预算 | 本地快不等于平台高可用 |
| 成本 | 每次成功入库/有效推荐的 token 与请求数 | 仅比较单次调用价格不反映整体成本 |
| 体验 | 观看后目标满足评分、再次选择意愿 | 不把停留时长直接当成满意度 |

## 优先候选一：检索质量与规模

**现状**：词法哈希基线依赖表达重叠，全量扫描向量，跨表达匹配和规模都有边界。

**可做的改动**：引入明确版本的中文语义 embedding，保留 BM25 形成真正的词法/语义混合检索；用本地向量索引替换全量扫描；在固定候选集上增加可缓存 reranker。

**验收方式**：相同独立测试集比较 BM25、当前基线、语义混合检索、加 reranker 的消融结果；同时报告 Recall/nDCG、P50/P95 延迟、索引大小、建立索引耗时和依赖成本。只有明确收益后才保留更复杂方案。

**保留的接口**：`chunks_for`、检索候选的时间戳/来源契约、推荐证据格式及目标级负反馈逻辑。

## 优先候选二：探索执行的可靠性与成本

**现状**：单 worker 顺序处理，已有预算与检查点；进程崩溃窗口仍可能重复外部请求，平台失败影响整轮耗时。

**可做的改动**：拆分采集/理解队列，增加按数据源的限流、内容指纹缓存和重试时间表；对字幕/帧状态设置不同刷新周期；并发采集保持有界，控制模型队列背压。需求足够明确后再考虑独立队列服务。

**验收方式**：注入限流、超时、进程退出、登录过期和重复提交；测量恢复后重复入库数、重复付费请求数、完成率、总耗时和成本。保留单用户下的简单部署能力，避免只增加组件数量。

**保留的语义**：取消不再启动新步骤、恢复沿用预算、低权限只读采集、外部文本不能变成执行指令。

## 后续产品研究，不作为第一阶段能力

“用户—Agent 系统—作者”三体系统可以在明确授权和数据隔离下扩展：创作者提供内容元信息或结构化证据，用户以可撤回授权分享聚合体验反馈，Agent 帮助发现内容供给与用户目标的错位。

这需要先回答：谁能看到哪些数据，反馈是否可聚合，样本是否足以评价作者，创作者是否可能为了被推荐而操纵描述。当前版本不把用户原始对话或个人反馈发送给作者，也没有创作者画像、作者排名或跨用户推荐模型。

“长期稳定放松”的判断也需要多次真实体验数据。未来可比较单视频满意与作者级稳定性，但不能从一条字幕或一次高评分推出长期可靠性。

## 建议选择顺序

1. 固定第一阶段接口、验收样例和失败案例。
2. 建立独立评估集，收集真实运行的瓶颈数据。
3. 在检索或执行两个方向中选一项为主、一项为辅。
4. 用消融、失败注入和可复现报告证明收益。
5. 再决定是否扩展多用户、创作者端或更自由的 Agent 策略。
